### 问题

类自己 new 依赖:new 数据库连接、new 邮件器——实现写死在内部。
换实现要改类的源码;测试想换成假的,无从下手;看构造函数签名,根本不知道这个类需要什么。

### 思路

依赖从外部传入,不在内部自建:构造函数声明「我需要什么」,由调用方/装配处决定给哪个实现。
创建的责任从使用方上移到装配点。

### 代码

```python
class OrderService:
    def __init__(self, repo, mailer):   # 依赖写在签名上
        self.repo, self.mailer = repo, mailer

# 生产:传真实实现
service = OrderService(PostgresRepo(), SmtpMailer())
# 测试:传假实现,不碰数据库不发邮件
service = OrderService(FakeRepo(), FakeMailer())
```

### 为什么有效

依赖关系全部显式:签名即文档。实现可替换、可测试——换实现不改类的源码,改的是装配那一行。
这是「面向接口编程」和「控制反转」的落地形式。

### 代价

对象要在一处装配(装配处/容器),小项目里这层显得绕;
依赖链很深时手写装配冗长——这时候才考虑容器,而不是先上容器再说。

### 与工厂 / 受控单例的关系

工厂回答「创建哪个实现」,但调用方还得知道工厂在哪;依赖注入连「要不要用工厂」都由装配处决定。
能传参就别用单例——依赖注入是默认答案,受控单例是例外。

### 什么时候用

需要替换实现的依赖(测试换假、多环境换真),以及希望依赖显式可见的任何时候。
**反例**——实现永远唯一且构造平凡的内部细节(比如一个字符串工具),注入是仪式。
