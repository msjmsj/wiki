# 概念详细讲解写作规程

> 一句话:先调研业界怎么讲,再套八节模板,纯中文写作,能配图就配图,写完 check 必须全绿。

适用对象:`tree/concepts/<kind>/<id>.md`(概念的详细讲解)。速记提示 `detail` 的规则见 tree-content 技能,本文件只管 doc。

## 写作流程(按顺序)

1. **调研先行**:用 search-toolbox 技能的方法(`web_search`,多角度 2-4 个 query),
   搜"这个模式/概念 业界怎么讲、最常见的误解是什么、和什么易混淆"。
   不要凭记忆直接写——观察者模式的调研发现了"商店到货困境""代价四连"这些好素材。
2. **套八节模板**(见下),不需要的小节可省,但顺序不变。
3. **写完跑 `./wiki check`**,警告必须清零。

## 八节模板(观察者模式沉淀,实测读者友好)

```
### 问题       不用它会怎样:一个具体场景 + 朴素写法 + 痛点暴露(每加一个就要改…)
### 思路       一句话点破反转/转化的关键,再给最小结构(一张表、两个方法)
### 结构       Mermaid 类图(角色用中文名)
### 时序       Mermaid 时序图:登记/调用/通知的先后顺序
### 代码       极简 Python(≤15 行):只展示骨架,英文标识符 + 中文注释;
               代码块不受纯中文约束,但只写结构不写完整实现
### 为什么有效  底层原理:依赖倒置/隔离变化点等第一性原理,不说"它能解耦"这种空话
### 代价       加粗缺点词 + —— 展开;写全:隐式流、顺序、泄漏、风暴…
### 与 X 的区别  高频混淆对象的对照(观察者 vs 发布订阅);没有就删这节
### 什么时候用  正面场景 + **反例**(什么时候别用)
```

要点:
- **问题小节是灵魂**:场景要具体到能认出来(气象站/面板),痛点是"每次都要改老代码"这种动作,不是抽象形容词
- **反例必填**:说清楚什么时候别用,比优点更能防止误用
- **对比小节**:挑读者最可能混淆的那个概念,说清"差在哪一层"

## 语言纪律(纯中文)

- 正文不出现英文术语:写「主题/观察者/登记/退订/通知」,不写 Subject/Observer/notify
- 英文原名只出现在概念的 `gof.aka` 字段(卡片徽章区),不进正文
- 需要强调段内要点时用 `**加粗**——破折号展开`,不要写「标签:」式行首(校验会拦)
- 代码标识符若必须出现,放代码块里,不混进散文

## Mermaid 配图规则

- 行为型模式优先**时序图**(谁先调用谁);结构型优先**类图**;状态流转用**状态图**;分层/流水线用 **graph TD**
- 节点名全部中文,如 `气象站 --|> 主题`
- 一概念至多两张图(结构 + 时序),图是辅助不是主角
- 写完后本地打开卡片确认图渲染正常(mermaid 语法错误会静默保留代码块)

## 机械约束(写完必跑 ./wiki check)

- doc 必须 `### 小节` 开头;不得残留旧式「标签:」段落(行首短词+冒号会误伤,用破折号替代)
- doc 不复读 detail(句子级原文检测)
- doc 里不留 TODO(脚手架骨架的占位必须补完)
- detail ≤ 80 字;detail 仍是纯文本,不写 Markdown

## 反面教训(已踩过的坑)

- 只写"定义+优点" → 读者学完不知道什么时候用、什么时候不该用
- 中英文混排("调用 notify 方法") → 阅读节奏断;术语一律中文化
- 只画类图不画时序图 → 行为型模式的"先后顺序"才是理解难点
- 写完不跑 check → 格式问题(旧式段落、复读 detail)会溜进去
